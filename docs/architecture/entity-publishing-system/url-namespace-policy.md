# URL Namespace Policy

Replaces the `/robot-parts/...` production assumption implied by PR #21's proposed site map with domain-neutral, stable namespaces, per the issue's explicit requirement.

## 1. The ten stable namespaces

```
/
├── /parts/           → pageType: part           (Part entity)
├── /assemblies/       → pageType: assembly        (Assembly entity)
├── /applications/     → pageType: application     (Application entity)
├── /capabilities/     → pageType: capability      (ProcessCapability entity)
├── /engineering/       → pageType: engineering     (EngineeringProblem entity)
├── /materials/         → pageType: material        (Material entity)
├── /resources/          → pageType: resource        (informational/guide, primaryEntityRef optional)
├── /quality/             → pageType: quality          (InspectionConcept entity)
├── /how-it-works/         → pageType: how_it_works     (trust/process content, primaryEntityRef optional)
└── /rfq/                    → pageType: rfq              (RFQ intake funnel, primaryEntityRef optional)
```

Each namespace corresponds 1:1 to a `pageRegistry.pageType` value (`page-registry.md` §1). A namespace is not itself a document type and carries no content of its own beyond the pages inside it — there is no `/parts/` "index" entity, only an index *page* (itself a `pageRegistry` record, `pageType: hub`, `canonicalPath: /parts/`) that renders a relational listing.

Examples from the issue, unchanged: `/parts/robot-joint-housing/`, `/parts/actuator-housing/`, `/applications/humanoid-robots/`, `/capabilities/5-axis-machining/`, `/engineering/bearing-fits/`.

## 2. Why no namespace encodes "robotics" (or any domain)

Every namespace above is a **page type**, never a **subject-matter domain**. This is the single mechanism that satisfies "the design must support adding future non-robotics applications... without changing existing canonical part/process/material URLs" (issue) and acceptance test 5. A `Part` (Robot Joint Housing) lives at `/parts/robot-joint-housing/` regardless of how many `Application`s (Humanoid, Industrial Robot Arm, future Industrial Automation Equipment) reference it — its path is a function of its own slug within `/parts/`, never of any `Application`, `Domain`, or navigation position. `future-domain-test.md` demonstrates this concretely by adding Industrial Automation Equipment and showing zero existing canonical paths change.

The `Domain` helper entity (`entity-relationship.md` §2.3) exists precisely so "Robotics" can be a real, editable, queryable grouping — used in nav menus, in an `/applications/` index page's section headers, in marketing copy — **without ever appearing in a path**. `Domain` has no `slug` field in the schema for exactly this reason (`sanity-schema-proposal.md` §5): it cannot accidentally become part of a URL because it has nothing to build one from.

## 3. Slug policy

- One slug per document, scoped uniquely within its own entity type (`sanity-schema-proposal.md` §1) — two `Part` documents can't share a slug, but a `Part` and an `EngineeringProblem` could coincidentally have the same slug text without conflict, because they live in different namespaces.
- Slugs are human-authored (Sanity's `source: 'name'` is a default suggestion, not an auto-lock) and reviewed at the same Human Gate as content, so a slug can be deliberately chosen for SEO/clarity rather than mechanically derived (e.g. `robot-joint-housing`, not `joint-housing-for-robots-and-similar-devices`).
- Slugs are **not** required to match the entity's `name` field verbatim, and `name` may change (e.g. a title rewrite for clarity) without forcing a slug — and therefore URL — change. Aliases (`Part.aliases[]`) absorb alternate phrasings without creating alternate URLs (invariant #14, "a single entity should have one canonical page by default").

## 4. No permutation surface (issue's hard rule, acceptance test 8)

There is no `country`, `material`, `process`, `lifecycle`, or `application` path segment anywhere in this policy, and no field in any Sanity schema (`sanity-schema-proposal.md` §7) that would let a script derive one. Concretely, none of the following can ever be generated by this system, because nothing computes a canonical path from a combination of entities — only a human-authored `PageRegistry.canonicalPath` field does:

```
✗ /parts/robot-joint-housing/7075-t6/            (part × material)
✗ /parts/robot-joint-housing/5-axis-machining/    (part × process)
✗ /parts/robot-joint-housing/humanoid/au/         (part × application × country)
```

If a genuinely distinct page is ever warranted for a specific part+material combination (rare, and would need its own search-intent evidence per `page-registry.md` §3.1), it gets its own explicitly-authored `pageRegistry` record and its own deliberately-chosen slug — it is still one human decision per page, never a batch/loop.

## 5. Canonical policy and redirects

- Every published page has exactly one canonical URL — its own `pageRegistry.canonicalPath`. A page never self-canonicalizes to another page except via the explicit `indexPolicy: canonical_redirect` + `redirectTarget` mechanism (`page-registry.md` §4).
- If a slug must change after publication (rare — e.g. correcting a typo, or a rename that survives a merge decision), the **old** `canonicalPath` should be re-registered as a new `pageRegistry` record with `indexPolicy: canonical_redirect` pointing at the entity's current record, rather than silently 404ing or relying purely on webserver-config redirects. This keeps the redirect itself reviewable/auditable content, consistent with everything else in the registry.
- **Unresolved (UQ-7, see `migration-plan.md`):** this pass does not decide the *mechanical* implementation of the redirect (a Next.js `redirects()` config entry generated from the registry at build time, vs. a runtime middleware lookup against live Sanity data). A static `next.config` list does not comfortably scale past a few hundred entries and would need regenerating on every registry change; a runtime lookup adds a request-time dependency. Left for a future BUILD-phase decision — see `rendering-revalidation.md` §4.

## 6. Future expansion rule

Adding a new `Application` (or a new `Domain` grouping of applications) never requires touching this file, the namespace list, or any existing `Part`/`Material`/`ProcessCapability`/`Assembly`/`EngineeringProblem` document's `canonicalPath`. It requires only: (1) a new `application` document, (2) optionally a new `domain` document if it doesn't fit an existing grouping, (3) new relation references from existing `Part`/`ProcessCapability`/`Material` documents into the new `Application` where genuinely applicable, and (4) a new `pageRegistry` record at `/applications/<new-slug>/`. See `future-domain-test.md` for this worked through with Industrial Automation Equipment end to end.
